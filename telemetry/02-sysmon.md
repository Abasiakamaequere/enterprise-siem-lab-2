# 02 — Sysmon Endpoint Telemetry

## Objective

Sysmon (System Monitor) was introduced into the Windows endpoint to provide enhanced visibility into system activity.

The purpose of adding Sysmon was to generate richer endpoint telemetry that could subsequently be collected by the Splunk Universal Forwarder and analyzed within Splunk Enterprise.

---

## Why Sysmon Was Added

Native Windows event logs provide important information about authentication, account activity, and system events.

However, security investigations often require additional visibility into endpoint behavior.

Sysmon provides telemetry that can support analysis of activities such as:

- Process creation
- Process relationships
- Network connections
- File-related activity
- Driver and system activity
- Other endpoint behaviors

This additional visibility improves the usefulness of the Windows endpoint as a security-monitoring data source.

---

# Sysmon as a Telemetry Source

Sysmon operates on the Windows endpoint and records detailed system activity into the Windows event infrastructure.

These events can subsequently be collected by the Splunk Universal Forwarder.

The resulting flow is:

```text
Endpoint Activity
       ↓
Sysmon
       ↓
Windows Event Log
       ↓
Universal Forwarder
       ↓
Splunk Enterprise
       ↓
SPL Search
```

This makes Sysmon an important component of the endpoint-to-SIEM telemetry pipeline.

---

# Security Value

The additional telemetry generated by Sysmon can help analysts answer questions that may not be possible to answer using authentication logs alone.

For example:

### Process investigation

An analyst may want to determine:

```text
Which process executed?
Who executed it?
When did it execute?
What process spawned it?
```

### Network investigation

An analyst may want to determine:

```text
Which process initiated a connection?
When did the connection occur?
Which destination was contacted?
```

### Threat hunting

An analyst can search endpoint telemetry for unusual combinations of:

```text
Process
+
User
+
Time
+
Network Activity
```

These relationships become particularly valuable when analyzed centrally in Splunk.

---

# Event Collection

Sysmon writes its telemetry into the Windows event infrastructure.

The Splunk Universal Forwarder is subsequently responsible for collecting the relevant event channel and forwarding the events to the Splunk server.

The architecture therefore separates:

```text
Telemetry Generation
```

from:

```text
Telemetry Collection
```

and:

```text
Telemetry Analysis
```

```text
Generation
    ↓
Sysmon

Collection
    ↓
Universal Forwarder

Analysis
    ↓
Splunk Enterprise
```

# Validation Objective

The successful Sysmon deployment must ultimately result in searchable endpoint telemetry within Splunk.

The validation chain is:

```text
Sysmon Installed
      ↓
Sysmon Events Generated
      ↓
Events Written to Windows Event Log
      ↓
Universal Forwarder Collects Events
      ↓
Events Forwarded to Splunk
      ↓
Events Become Searchable
```

A successful installation by itself is therefore not considered sufficient.

The final objective is **observable telemetry inside the SIEM**.

---

# Troubleshooting Considerations

Endpoint telemetry collection introduces several possible failure points.

If Sysmon events do not appear in Splunk, the investigation should proceed through the telemetry pipeline rather than immediately assuming that Splunk is malfunctioning.

```text
1. Is Sysmon running?
        ↓
2. Are Sysmon events being generated?
        ↓
3. Are events present in Windows Event Log?
        ↓
4. Is the Universal Forwarder running?
        ↓
5. Is the correct event channel being monitored?
        ↓
6. Can the Forwarder reach TCP 9997?
        ↓
7. Is Splunk receiving the events?
        ↓
8. Are the events searchable?
```

This layered troubleshooting model is important for diagnosing endpoint telemetry failures.
