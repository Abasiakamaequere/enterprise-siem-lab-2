# 03 — Network Activity Monitoring

## Objective

The objective of this detection is to monitor network activity generated by the Windows endpoint and use that activity as additional context during security investigations.

Network telemetry can help analysts understand whether a process or user activity resulted in communication with another system or destination.

Within this laboratory, network activity is analyzed alongside authentication and process telemetry.

The network-monitoring stage builds on the process-execution visibility established in Detection 02 and provides an additional dimension for correlation and investigation.

---

# Detection Data Source

Network-related telemetry can originate from endpoint monitoring data collected through Sysmon.

Sysmon network connection events are commonly associated with:

```text
Event ID 3
````

The exact availability of this event depends on the Sysmon configuration deployed on the Windows endpoint.

Where available, the event can provide context about network connections associated with endpoint processes.

The laboratory therefore treats Sysmon network telemetry as an additional investigative source rather than assuming that every network connection is automatically available or security-relevant.

---

# Basic Network Search

A basic search for Sysmon network connection events can be structured as:

```spl
index=* EventCode=3
```

This provides a starting point for examining Sysmon network connection events.

The actual index and field names should be validated against the telemetry ingested by the laboratory.

---

# Network Investigation

A network event should not automatically be classified as malicious.

The analyst should establish context around the connection.

Important questions include:

```text
Which process initiated the connection?
        ↓
Which user was associated with the activity?
        ↓
What destination was contacted?
        ↓
Which destination port was used?
        ↓
When did the connection occur?
        ↓
Was the communication expected?
```

This approach prevents individual network events from being interpreted without sufficient context.

---

# Process-to-Network Correlation

One of the primary advantages of endpoint network telemetry is the ability to associate network activity with process execution.

The investigation model is:

```text
Process Execution
       ↓
Process Identity
       ↓
Network Connection
       ↓
Destination
```

This allows the analyst to ask:

> Which process was responsible for the observed network activity?

This is more useful than examining an IP address or connection event without endpoint context.

---

# Example SPL

A basic investigation view can be created using:

```spl
index=* EventCode=3
| table _time host user Image SourceIp SourcePort DestinationIp DestinationPort
```

The exact field names should be confirmed against the actual Sysmon events in the environment.

---

# Destination Analysis

Network connections can be grouped by destination to identify frequently contacted systems.

Example:

```spl
index=* EventCode=3
| stats count by DestinationIp
| sort - count
```

This can help establish a baseline of normal communication within the laboratory.

A high connection count by itself does not indicate malicious activity.

---

# Port Analysis

Destination ports can also provide useful context.

Example:

```spl
index=* EventCode=3
| stats count by DestinationPort
| sort - count
```

This allows the analyst to identify commonly observed destination ports.

Unusual ports may warrant further investigation, but port number alone is not sufficient evidence of malicious activity.

---

# Process Analysis

Network activity becomes more valuable when grouped by process.

Example:

```spl
index=* EventCode=3
| stats count by Image
| sort - count
```

This can help identify which processes are responsible for the greatest amount of observed network activity.

Again, frequency is contextual rather than inherently malicious.

---

# Network Activity Timeline

A time-based view can help identify periods of increased network activity.

```spl
index=* EventCode=3
| timechart count
```

The resulting timeline can be compared with:

* Authentication events
* Process creation
* User activity
* Other endpoint telemetry

This provides a stronger investigative picture.

---

# Authentication-to-Network Correlation

Authentication activity can be examined together with network activity.

For example:

```text
Authentication
      ↓
User Session
      ↓
Process Execution
      ↓
Network Connection
```

This sequence can help an analyst determine what happened following a particular authentication event.

---

# Process-to-Network Correlation

The process-monitoring detection can also be connected directly to network activity.

```text
Sysmon Process Creation
        ↓
Identify Process
        ↓
Identify User
        ↓
Identify Network Connection
        ↓
Identify Destination
```

This allows an investigation to move from:

> What executed?

to:

> What did the process communicate with?

This correlation is particularly useful when investigating controlled reconnaissance or other endpoint activity that may generate both process and network telemetry.

---

# Controlled Activity Context

The laboratory includes controlled reconnaissance activity used to validate endpoint monitoring and detection workflows.

The process-monitoring stage demonstrated controlled execution of:

```text
whoami.exe
```

associated with:

```text
T1033 — System Owner/User Discovery
```

The process event was successfully observed within Splunk after the endpoint telemetry pipeline was corrected.

Network telemetry can provide additional context around such activity where the relevant Sysmon network events are available.

The existence of network activity associated with a controlled test does not by itself establish malicious behavior.

---

# Investigative Questions

When examining an unusual network connection, the analyst should consider:

### Source

* Which endpoint generated the connection?
* Which user was associated with the activity?

### Process

* Which process initiated the connection?
* Was that process expected?
* Where was the executable located?

### Destination

* Which IP address or destination was contacted?
* Is the destination expected within the laboratory?

### Port

* Which destination port was used?
* Is the port consistent with the expected service?

### Timing

* When did the connection occur?
* Did it occur immediately after process execution?
* Did it occur after a suspicious authentication event?

---

# Detection Logic

A potentially suspicious network event should be evaluated using multiple dimensions:

```text
Network Connection
        +
Process
        +
User
        +
Destination
        +
Port
        +
Time
```

The combination of these attributes provides stronger analytical context than any single field.

---

# Example Investigation Workflow

```text
Unusual Network Connection
          ↓
Identify Source Host
          ↓
Identify User
          ↓
Identify Process
          ↓
Inspect Process Path
          ↓
Inspect Destination
          ↓
Inspect Destination Port
          ↓
Review Authentication Events
          ↓
Review Process Creation Events
          ↓
Determine Whether Activity Is Suspicious
```

This workflow demonstrates the progression from an individual network event toward contextual security analysis.

---

# False Positive Considerations

Normal endpoint activity can generate large volumes of network connections.

Examples include:

* Operating-system services
* Software updates
* Browser activity
* DNS resolution
* Security software
* Background applications
* Virtual machine services

Therefore, a network connection should not be classified as malicious solely because it is:

* Uncommon
* External
* Associated with a particular port
* Associated with a high connection count

Context is required.

---

# Detection Limitations

The basic network searches in this document are intended for monitoring and investigation.

A production-quality detection would require additional context such as:

* Asset information
* Known-good destinations
* Process baselines
* User context
* Network segmentation
* Destination reputation
* Time-based thresholds
* Allowlisting
* Correlation with other security events

The laboratory's network-monitoring capability should therefore be considered an investigative foundation rather than a complete network detection platform.

---

# MITRE ATT&CK Context

Network connection telemetry can support investigations across multiple ATT&CK techniques depending on the observed behavior.

The presence of a network connection alone does not establish a specific ATT&CK technique.

ATT&CK mapping should therefore be based on the complete behavior and investigation evidence.

For the controlled reconnaissance activity documented in the process-monitoring stage, the relevant behavior was mapped to:

```text
T1033 — System Owner/User Discovery
```

The technique mapping applies to the controlled reconnaissance behavior and should not be inferred solely from a generic network connection event.
